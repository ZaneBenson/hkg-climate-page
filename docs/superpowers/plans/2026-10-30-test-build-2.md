# hkg-climate-page Plan 3: test build 2 (seat buttons send the approved command)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** With the owner's approval switch on, a tap on a seat button sends one step of the approved seat command through the stock seat service; with it off (the default), the build behaves exactly like test build 1.

**Architecture:** All new logic stays in the app; the panel page and its patch are unchanged.
- **Core:** `ClimateCore` gets an approval flag that picks the real sender or the log-only commander, and drives the page's test-mode strip.
- **Pure Java (host-tested):** a `CheckedSeatSender` refuses any value outside the confirmed list and records each result, and a `SendWatch` notices when the car doesn't follow a send.
- **Android:** a thin `UsmCalls` adapter is the only code that touches `com.hkmc.usm.USMManager`. The settings screen's approval switch becomes real.

**Tech Stack:** as plan 2. Java 8 against API 19, JUnit 4.13.2, the existing build scripts and checks.

**Spec:** `docs/superpowers/specs/2026-10-30-hkg-climate-page-design.md`. Approval record: `docs/notes/2026-10-30-status-and-findings.md`, "Seat command approval (2026-10-30)".

## Global Constraints

- The approved command (owner, 2026-10-30) is all a build may send:
  - `com.hkmc.usm.USMManager.setFrontSeatHeatDrvStep(int)` for the driver, `setFrontSeatHeatAstStep(int)` for the passenger;
  - values only 2, 3, 4, 5, 6, 7, 8 (2 off; 8/7/6 heat high/mid/low; 5/4/3 cool high/mid/low).
- Sending happens only from a tap on the page, one step per tap, only while the approval switch is on. Nothing is sent at boot, on a state update, on an approval change, on a switch-temperature change, or as a retry.
- The approval switch is off by default and stored in the app's preferences (`seat_command_approved`). An app update through NEMESIS reinstalls the app, so it resets to off.
- While approval is off, taps log `would set <method> <value>`, as in test build 1. While it is on, they log `sent <method> <value>`, or `send refused <method> <value>` / `send failed <method> <value>: <exception>`. Tag `HkgClimate`.
- The panel patch (`panel/`, `package/patch/*`) does not change. The page hides the yellow strip when the state says `testMode` is false.
- No manufacturer code in the repo. The new stub `com.hkmc.usm.USMManager` declares only the three members used.
- Version `0.2.0-test2` (versionCode 2), for both the APK and NEMESIS.data.
- Commits: plain words, ending `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **Approval on, then the service restarts or the car boots:** nothing is sent until a tap. Test in Task 1.
2. **The stock service refuses our app** (`SecurityException`, `RemoteException`, missing class): no crash; the result reads `send failed …` in the log and on the settings screen; the next tap tries again, once. Test in Task 2.
3. **A value outside 2..8 ever reaches the sender:** it is refused and never passed on. Test in Task 2.
4. **The seat doesn't follow a send within 3 s** (the car ignored it): logged and shown on the settings screen. Test in Task 2.
5. **Approval turned off between two taps:** the second tap only logs `would set`. Test in Task 1.

### Task 2: Checked sender and send watch (pure Java)

**Files:**
- Create: `core/src/hkgclimate/core/{UsmCalls,SendLog,Clock,CheckedSeatSender,SendWatch}.java`
- Test: `core/test/hkgclimate/core/{CheckedSeatSenderTest,SendWatchTest}.java`

**Interfaces:**
- Produces:
  - `interface UsmCalls { void driver(int value) throws Exception; void passenger(int value) throws Exception; }`
  - `interface SendLog { void line(String text); }`: the Android side writes the line to the log.
  - `CheckedSeatSender implements SeatCommander`: constructor `(UsmCalls calls, SendLog log, SendWatch watch, Clock clock)`, where `interface Clock { long now(); }` is our own (Android 4.4 has no `java.util.function`, so core must not use it in code the app ships). On `set`:
    - a value with `!SeatValues.isKnown(value)` logs `send refused <method> <v>`, records it, and makes no call;
    - otherwise it calls `calls.driver/passenger(v)`, logs `sent <method> <v>` and calls `watch.sent(seat, v, now)`;
    - any Throwable from the call logs `send failed <method> <v>: <Throwable.toString()>` and records it.

    `String lastResult()` returns the last logged text, or null before any. `<method>` is `setFrontSeatHeatDrvStep` / `setFrontSeatHeatAstStep`.
  - `SendWatch`, with `WAIT_MS = 3000`:
    - `sent(Seat, int value, long now)` replaces any earlier pending send for that seat;
    - `onState(Seat, int value)` clears the pending send when the value matches;
    - `String overdue(long now)` returns `no change after 3 s: <method> <v>` for the oldest pending send older than `WAIT_MS` and clears it, else null.
